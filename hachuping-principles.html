02

2D 깊이를 3D 공간으로

핵심 CV 파트

역투영 — 픽셀 하나를 3D 점으로

깊이맵의 한 픽셀 (u, v)와 그 깊이 d가 있을 때, 그 점이 방 안 어디인지를 계산한다. 여기서 딱 하나만 틀려도 방 전체가 어긋난다: 깊이는 광선의 길이가 아니라, 카메라 −Z 축에 내린 수직거리다.

src/depth-math.jsL30–44 · depthSampleToWorld()
// 이미지 좌표는 좌상단 원점, NDC 는 y 가 위 → v 뒤집기
const xNdc = u * 2 - 1;
const yNdc = (1 - v) * 2 - 1;

// 근평면 클립 좌표를 역투영해 카메라 좌표계의 광선을 얻는다
const ray = multiplyMat4Vec4(invProjection, [xNdc, yNdc, -1, 1]);
const vx = ray[0] / ray[3];
const vy = ray[1] / ray[3];
const vz = ray[2] / ray[3];
if (!(vz < 0)) return null; // 카메라 앞이어야 한다

// Scale the ray so its perpendicular (view-Z) distance equals the depth.
const scale = depth / -vz;
const world = multiplyMat4Vec4(viewMatrix, [vx * scale, vy * scale, vz * scale, 1]);
이 14줄이 “2D 영상 → 3D 공간”의 전부다. 나머지는 이것을 몇만 번 반복해서 누적하는 이야기다. three.js 의존이 없어 PC에서 단위 테스트로 검증된다.

키프레임 — 왜 매 프레임을 쓰지 않는가

가만히 서 있는 60프레임은 새 정보가 0인데, 같은 점을 60번 세면 “여러 번 관측됐으니 진짜다”라는 판정이 무너진다. 그래서 직전 키프레임 대비 20 cm 이동 또는 15° 회전했을 때만 깊이를 읽는다.

src/keyframe-gate.jsL23–33 · isKeyframe()

깊이 필터 — 경계의 유령 점 버리기

ARCore의 깊이맵은 깨끗하지 않다. 값이 아예 없는 픽셀(투명·반사 물체, 너무 가까운 손), 신뢰 구간 밖의 값, 그리고 물체 경계에서 생기는 flying pixel을 순서대로 거른다.

TSDF fusion — 지도를 만드는 방식

가장 중요한 개념이다. 방을 5 cm 복셀 격자로 나누고, 각 복셀에 “가장 가까운 표면까지의 부호 있는 거리”를 저장해 프레임마다 평균낸다. 표면은 그 평균값이 0을 가로지르는 곳이다.

src/tsdf-grid.jsL147–163 · integrate()
// Band: [L - tau, L + tau], signed distance measured along the ray.
const bandStart = Math.max(length - tau, 0);
const bandSteps = Math.round((length + tau - bandStart) / step);
for (let i = 0; i <= bandSteps; i += 1) {
  const t = bandStart + i * step;
  const sdf = Math.max(-1, Math.min(1, (length - t) / tau));
  this._fuse(cam[0] + ux*t, cam[1] + uy*t, cam[2] + uz*t, sdf, frameId, true, obsWeight);
}

// Free space: the ray got here, so nothing solid sits along it.
if (col % carveStride === 0 && row % carveStride === 0 && bandStart > carveStart) {
  const carveSteps = Math.floor((bandStart - carveStart) / step);
  for (let i = 0; i < carveSteps; i += 1) {
    const t = carveStart + i * step;
    this._fuse(cam[0]+ux*t, cam[1]+uy*t, cam[2]+uz*t, 1, frameId, false, obsWeight);

드리프트와 앵커 — 좌표계가 흔들리는 문제

AR에서 가장 배신당하기 쉬운 부분이다. local 기준 공간의 원점은 “세션 시작 시 폰이 있던 곳”인데, 이것은 추적기가 계속 수정하는 추정치다. 무늬 없는 복도를 걸었다 돌아오면 ARCore가 자기 위치 추정을 툭 보정하는데, 우리가 저장해둔 8만 개 복셀 좌표는 따라 움직이지 않는다.

src/map-anchor.jsL107–124 · 좌표계 왕복
toWorld([x, y, z]) {                // 지도 좌표 → 현재 월드 (그릴 때)
  const r = rotate(this.orientation, [x, y, z]);
  return [r[0] + this.position[0], r[1] + this.position[1], r[2] + this.position[2]];
}

toAnchor([x, y, z]) {               // 현재 월드 → 지도 좌표 (저장할 때)
  const [qx, qy, qz, qw] = this.orientation;
  return rotate([-qx, -qy, -qz, qw],
    [x - this.position[0], y - this.position[1], z - this.position[2]]);
}
앵커를 지원하지 않는 기기에서는 포즈가 항등(identity)으로 남아 두 함수가 그대로 항등함수가 된다. 호출부는 지원 여부를 분기하지 않는다 — 고정 local 폴백.
03

하츄핑을 그 위에 얹기

정합 · 정규화 · 가림

하츄핑의 위치는 지도(앵커) 좌표계에 있고, 렌더링 직전에 toWorld()로 현재 월드 좌표로 변환된다. three.js의 WebXR 매니저가 가상 카메라를 매 프레임 XRViewerPose에 맞춰 놓기 때문에 가상 카메라와 실제 카메라의 투영행렬이 동일해지고, 그려진 픽셀이 영상 위 정확한 자리에 앉는다.

모델 정규화

스캔한 GLB는 자기 마음대로의 스케일과 원점을 갖고 온다. 바운딩 박스로부터 높이 34 cm에 맞추는 균일 스케일과 바닥이 y = 0에 닿고 수평 중심이 원점에 오는 오프셋을 계산해 “표면 위에 서 있는 모델”로 만든다.

가림(occlusion) — 완전히 다른 두 방식

현실 물체가 하츄핑을 가리려면, 현실의 거리가 렌더러의 깊이 버퍼에 들어와야 한다. 이 프로젝트에는 그 방법이 두 가지 있고, 모드마다 다른 쪽을 쓴다.

// 시야 방향에 수직인 가로축 — 카메라가 실제로 마주하는 실루엣

const sz = planar > 1e-6 ?  dx / planar : 0;

  [0, 0, 0],                                  // centre of mass

이 7점을 정의하는 곳은 line-of-sight.js지만, 검거 판정이 실제로 쓰는 것은 live-visibility.js — 지금 이 프레임의 깊이 영상에 대고 같은 7점을 묻는 쪽이다. 같은 파일의 복셀 지도 판정(segmentBlocked)은 게임에서 더 이상 호출되지 않는다. 얼어붙은 지도는 드리프트에 대해 정직하지 않기 때문이다.

04

“무엇이 있다”를 “설 수 있다”로

통행 격자

복셀 지도는 점유만 안다. 도망은 “여기 설 수 있나, 여기서 저기로 갈 수 있나”가 필요하다. 방을 위에서 내려다본 20 cm 셀 격자로 투영하고, 셀마다 높이를 10 cm 슬랩으로 쪼개 점유 여부를 64비트 비트마스크로 저장한다.

src/traversal-grid.jsL444–468 · levels()
for (let slab = 0; slab < this.slabCount; slab += 1) {
  if (!this.hasSlab(cell, slab)) continue;
  // Too high above the floor to be anywhere a small character could get.
  if (this.slabTopY(slab) > ceiling) break;
  if (slab + this.headroomSlabs >= this.slabCount) break;
  let clear = true;
  for (let above = 1; above <= this.headroomSlabs; above += 1) {
    if (this.hasSlab(cell, slab + above)) { clear = false; break; }
  }
  if (clear) levels.push(this.slabTopY(slab));
}
설 수 있다 = 점유된 슬랩 + 위로 몸 높이(34 cm)만큼 비어 있음 + 바닥에서 0.85 m 이내.

노이즈를 막는 3중 방어

  • 슬랩당 최소 4개 복셀 — 점 하나로 20×20 cm 발판이 생기지 않게. 완전히 관측된 평평한 바닥은 슬랩에 16개를 남기므로 4는 여유롭다.
  • 바닥 히스토그램 — Y축 히스토그램에서 셀이 가장 많이 몰린 슬랩을 바닥으로 잡는다. 바닥 높이를 정하는 것은 이것 하나뿐이다.
  • hasRaisedSupport — 바닥에서 40 cm 이상 뜬 발판은 8-이웃 중 최소 2개가 비슷한 높이의 발판을 가져야 인정. 진짜 책상은 8/8, 허공의 노이즈 덩어리는 0/8.

지도를 얼린다 — 스캔과 플레이를 가르는 선

지도는 맵 생성 단계에서만 자란다. 맵 생성 종료를 누르는 순간 freezeMap()이 깊이 공급을 끊고, 이후 도망·검거는 얼어붙은 지도 위에서만 돈다. 플레이 중에는 복셀 하나도 추가되지 않는다.

왜 얼리는가

뛰고 있는 경로 밑에서 지형이 바뀌면 안 되기 때문이다. A*가 계산한 경로의 한 칸이 다음 프레임에 사라지면 하츄핑은 허공을 딛는다. 게다가 플레이 중에는 폰이 하츄핑을 쫓느라 빠르게 흔들려서 스캔 품질이 가장 나쁜 구간이다 — 그 관측을 지도에 섞으면 맵 생성 때 공들여 모은 것을 오염시킨다. 얼리는 대신 가림 판정만 실시간 깊이를 쓴다.

시작 조건도 여기서 걸린다. 걸을 수 있는 칸이 70칸(약 2.8 m²)에 못 미치면 도망이 시작되지 않고 “지도가 아직 부족합니다”가 뜬다. 이 문턱은 가장 얇은 정직한 스캔보다 아래에 있어야 한다 — 높게 잡으면 짧게 걸은 방에서 하츄핑이 조용히 영영 나타나지 않는다.

선택 사항 · ?floor=ransac

성긴 바닥에 구멍이 많을 때를 위한 옵션이다. 복셀에 RANSAC으로 수평에 가까운 평면을 맞춰 “일관된 바닥이 존재한다”를 확인하고, 그 근거로 관측이 빠진 칸을 메운다. 다만 평면의 높이는 쓰지 않는다 — 밀도가 가장 높은 면이 책상일 수도, 가장 낮은 점이 마룻바닥 아래 노이즈일 수도 있어서, 실제로 하츄핑이 바닥 밑으로 가라앉은 적이 있다. 높이는 어디까지나 히스토그램이 정하고, 평면은 구멍 메우기에만 쓴다.

  : Math.max(0, levels[level] - floorY - this.slabHeight / 2) * this.heightTollPerM;

out.push({ cx: nx, cz: nz, level, rise, move: jump ? MOVE.JUMP : MOVE.WALK,
           cost: planar + jumpCost + heightToll });

목적지를 언제 갈아타는가

매 프레임 경로를 따라 전진하되, 목적지를 다시 고르는 것은 세 경우뿐이다 — 도착했거나, 전진이 멈췄거나, 3초가 지났고 동시에 그 목적지가 실제로 나빠졌을 때. 마지막 조건의 “나빠졌다”는 플레이어가 그 목적지에 하츄핑보다 가까워진 것을 뜻한다. 그대로 달려가면 플레이어 품으로 뛰어드는 셈이기 때문이다.

src/chase-runner.jsL380–396 · ensurePath()

순수한 3초 타이머였다면 안 된다. 조금 멀거나 올라가야 하는 목적지는 3초 안에 닿지 못하는데, 매번 타이머가 갈아치우면 영영 도착하지 못한다. 실제로 그렇게 돌던 시절 가구 목적지의 84%가 걸어가는 도중에 폐기됐고, 그래서 하츄핑이 의자 위에 있는 모습을 거의 볼 수 없었다. 지금은 가고 있는 목적지는 웬만하면 끝까지 간다.
  • 끼임 탈출 — 재계획이 3회 연속 실패하면 플레이어 쪽으로 격자 엣지를 무시한 한 칸을 만들어 활강한다. 위에서 말한 “구조적으로 불가능”을 의도적으로 깨는 유일한 지점이다. 지도가 아무 데와도 이어지지 않는 노이즈 섬에 갇혔을 때, 벽을 스치더라도 빠져나오는 편이 벽 안에 얼어붙어 있는 것보다 낫다. 플레이어가 있는 곳은 반드시 스캔된 진짜 공간이므로 그쪽으로 가면 유효한 지형을 다시 만난다.
  • 추적 손실 — viewerPose가 없으면 하츄핑도 setFrozen(true)로 멈춘다. 추적 끊김이 공짜 도주가 되면 안 된다.
  • 피로 — 게이지가 0.4를 넘으면 속도 0.7배, 0.7을 넘으면 0.45배. 추격의 마지막 구간이 수렴한다.

노이즈를 견디는 게임 규칙

잡기 게이지

세 조건이 동시에 만족되면 게이지가 찬다 — 거리 2 m 이내, 화면 중심에서 20° 이내, 그리고 가시도. 5초를 채우면 검거다. 여기서 중요한 것은 조건을 놓쳤을 때 리셋이 아니라 감쇠라는 점이다.

src/capture-gauge.jsL129–169 · update()

this.onScreen = angleDeg <= this.angleDeg;  // 20°

// 깊이 노이즈로 값이 깜빡이므로 약 1/4 초에 걸쳐 이징

  ? this.fillPerSecond * dt * this.visibleScale
  : -this.decayPerSecond * dt;
this.value = Math.min(1, Math.max(0, this.value + step));
if (this.value >= 1) this.captured = true;
scaleForVisibility()는 절대 0을 반환하지 않는다 — 완전히 가려져도 0.25배로는 찬다. 가시도는 실시간 깊이 영상에 대고 7점을 묻는 값인데, 2 m 거리의 20 cm 캐릭터는 깊이 격자에서 몇 셀밖에 되지 않아 앞에 아무것도 없는데 전부 가려짐으로 읽히는 순간이 있다. 그때 게이지가 아예 멈추면 게임이 얼어붙은 것처럼 보인다.

depth-math, tsdf-grid, traversal-grid, chase-path, chase-runner, line-of-sight, capture-gauge — 전부 three.js·DOM·WebXR을 import 하지 않는다. WebXR은 실기기 없이는 실행조차 안 되므로, 폰을 꺼내야만 확인 가능한 코드의 비율을 줄이는 것이 개발 속도를 좌우한다. 456개 테스트가 PC의 node --test로 돌고, TSDF 융합은 저장된 스캔 JSON에 대해 폰에서 도는 것과 완전히 동일하게 재실행된다.
