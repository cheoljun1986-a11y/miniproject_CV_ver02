# WebXR Hidden Ninja v2

브라우저(WebXR)만으로 **ARCore 공간추적 + 실세계 오클루전 + 2D 영상의 3D 공간 복원**을
검증하는 AR 숨바꼭질 미니프로젝트. 설치 없이 Android Chrome에서 HTTPS 주소만 열면 동작한다.

- 공개 데모: <https://cheoljun1986-a11y.github.io/miniproject_CV_ver02/>
- CPU 동적 가림 + 통합 모드: <https://cheoljun1986-a11y.github.io/miniproject_CV_ver02/?occlusion=cpu>
- 공간 복원 진단 모드: <https://cheoljun1986-a11y.github.io/miniproject_CV_ver02/?depth=cloud>
- 하츄핑 도망 모드: <https://cheoljun1986-a11y.github.io/miniproject_CV_ver02/v4-chase.html>
- 키프레임 복셀 진단 모드: <https://cheoljun1986-a11y.github.io/miniproject_CV_ver02/?voxel=debug>

> **이 문서는 발표 자료로 쓸 수 있도록 시계열로 정리했다.**
> 3장 타임라인 표가 목차, 4장의 각 단계가 슬라이드 한 장에 대응한다.

## 1. 프로젝트 개요

Ninja(닌자)를 현실 공간 한 곳에 숨기고, 사용자가 직접 걸어다니며 찾는 AR 게임이다.
게임 자체가 목적이라기보다, **폰 한 대(WebXR/ARCore)만으로 어디까지 되는지**를 검증하는
feasibility 테스트에 가깝다. 특히 컴퓨터비전 관점에서 핵심은:

> **움직이는 카메라의 2D 영상 → 3D 공간으로 복원하고, 그 위에 가상 물체를 정합·가림 처리한다.**

프로젝트 전반을 관통하는 제약은 세 가지였다.

| 제약 | 이유 |
|---|---|
| **백엔드 없음 · 정적 호스팅** | GitHub Pages에 그대로 올려 폰에서 URL만으로 접속 |
| **번들러 없음 · 브라우저 네이티브 ES 모듈** | 설치·빌드 단계를 없애 실기기 확인 주기를 짧게 |
| **순수 로직은 three.js 비의존** | 폰 없이도 PC에서 `node --test`로 검증 가능하게 |

## 2. 핵심 아이디어: 2D 영상 → 3D 공간

```
[카메라 2D 영상 + 폰 센서(IMU)]
        │  ← ARCore 담당 (depth-from-motion / SLAM)
        ▼
[6DoF 카메라 포즈]  +  [픽셀별 깊이맵(depth map)]
        │  ← 우리 담당 (역투영 unprojection)
        ▼
[각 깊이 픽셀 → 3D 월드 좌표]  →  누적/복셀화  →  3D 공간(포인트클라우드)
        │
        ▼
[그 위에 Ninja 배치 · 실세계 물체로 가림(occlusion)]
```

- **ARCore**: 여러 각도의 2D 프레임과 관성센서로 카메라 위치와 깊이를 추정한다.
- **우리 코드**: 그 깊이를 카메라 투영행렬·포즈로 3D 점으로 되돌리고(역투영), 누적한다.
  즉 순수 RGB로 직접 포토그래메트리를 하는 게 아니라, **ARCore가 준 깊이를 3D로 복원**한다.

> 아래 2-1 ~ 2-6은 **발표용 원리 설명**이다. 위 흐름도를 용어·좌표계·실제 숫자 단위까지
> 풀어 쓴 것으로, "우리가 정확히 무엇을 계산하는가"를 한 프레임 단위로 추적한다.

### 2-1. 용어 정리

| 약어 | 풀이 | 뜻 |
|---|---|---|
| **AR** | Augmented Reality | 증강현실 |
| **ARCore** | AR + Core | 구글이 만든 안드로이드용 AR 엔진. 폰 안에서 동작 |
| **IMU** | Inertial Measurement Unit | 관성 측정 장치. 자이로스코프 + 가속도계 |
| **VIO** | Visual-Inertial Odometry | 시각-관성 주행거리 측정. 카메라 + IMU로 위치 추적 |
| **SLAM** | Simultaneous Localization And Mapping | 동시적 위치추정 및 지도작성 |
| **WebXR** | Web + eXtended Reality | 브라우저에서 AR/VR을 쓰게 해주는 웹 표준 |
| **6DoF** | Six Degrees of Freedom | 6자유도. 위치 3축 + 회전 3축 |
| **NDC** | Normalized Device Coordinates | 정규화 장치 좌표. 모든 축이 −1 ~ +1 |
| **ToF** | Time of Flight | 비행 시간 방식 깊이 센서 (하드웨어) |

**IMU가 왜 필요한가** — 카메라와 IMU는 약점이 정확히 반대다.

| | 카메라 | IMU |
|---|---|---|
| 갱신 속도 | 느림 (30~60Hz) | 빠름 (수백~1000Hz) |
| 빠른 움직임 | 모션 블러로 실패 | 문제 없음 |
| 어두운 곳 / 흰 벽 | 특징점 없어 실패 | 문제 없음 |
| 오차 성질 | 정확하나 가끔 완전히 틀림 | 항상 조금씩 틀리고 **누적됨** |

그래서 둘을 합쳐 쓰는 것이 VIO다. 카메라가 절대 위치를 보정하고, IMU가 순간 추적을 담당한다.

**"광선(ray)"은 레이저가 아니다** — 렌즈 중심에서 픽셀 방향으로 뻗는 *수학적 직선*이다.
폰이 무언가를 쏘지 않는다. 깊이는 **depth-from-motion**, 즉 폰이 움직이며 찍은 두 시점의
**시차(parallax)** 를 삼각측량해 얻는다. 그래서 다음이 전부 설명된다.

- 가만히 서 있으면 깊이가 안 나온다 → 시차가 안 생김
- 흰 벽에서 깊이가 엉망이다 → 특징점 매칭 실패
- 멀수록 오차가 커진다 → 시차가 작아져 오차가 증폭 → 코드의 `MAX_RANGE_M = 6` 근거

일부 기기의 ToF/LiDAR 센서가 있으면 ARCore가 함께 쓰지만, **WebXR API는 양쪽을 동일하게
"픽셀별 미터 값"으로 넘기므로 이 앱 코드는 어느 쪽인지 알 필요가 없다.**

### 2-2. 좌표계와 원점 — (0,0,0)은 어디인가

**축 규약** (WebXR = three.js 동일, 오른손 좌표계)

```
        +Y  (위, 중력 반대)
         |
         |
         +------ +X  (오른쪽)
        /
      +Z  (뒤쪽 = 내 몸 쪽)

   카메라가 보는 방향은 -Z 다 (+Z 아님)
```

카메라가 −Z를 본다는 규약이 코드에 그대로 있다.

```js
// src/depth-math.js:39
if (!(vz < 0)) return null; // must be in front of the camera
```

**원점은 고를 수 있다.** WebXR의 참조 공간(reference space) 종류:

| 종류 | (0,0,0) 위치 | 비고 |
|---|---|---|
| `viewer` | 폰 자신 (항상 원점) | 폰이 움직이면 원점도 이동 |
| `local` | **세션 시작 순간의 폰 위치** | 이 프로젝트가 쓰는 것 |
| `local-floor` | 시작 위치 바로 아래 **바닥** | y=0이 바닥 |
| `unbounded` | 넓은 영역용 | 지원 기기 제한적 |

**이 프로젝트는 `local`을 쓴다. 두 곳에서 설정하며, 반드시 같아야 한다.**

```js
// src/xr-session.js:24  — 앱이 좌표를 읽을 기준
this.localSpace = await this.session.requestReferenceSpace('local');
// src/main.js:84        — three.js가 화면을 그릴 기준
renderer.xr.setReferenceSpaceType('local');
```

> ⚠️ 한쪽만 `local-floor`로 바꾸면 렌더 좌표계와 계산 좌표계가 사람 키(약 1.2m)만큼
> 어긋난다. Ninja가 바닥을 뚫고 나타나는 식이다. 바꾼다면 **두 줄을 함께** 고쳐야 한다.

```
        [START AR 을 누른 순간]

              (폰)  <- 이 지점이 (0, 0, 0)
               |
               |  약 1.2m
               |
        =======+==============  실제 바닥 ~ y = -1.2
```

| 축 | 무엇으로 정해지나 |
|---|---|
| 원점 | 그 순간 폰이 있던 위치 |
| **Y축** | **중력 반대 방향.** IMU 가속도계가 중력을 감지 → 항상 물리적 수직 |
| −Z축 | 그 순간 폰이 바라보던 수평 방향 |

**Y축만 물리적 의미가 있고, X/Z 방향은 시작 시 어디를 봤느냐에 따라 매번 달라진다.**

#### 이 선택이 코드에 남긴 결과

**① y=0은 바닥이 아니다.** 복셀 색상 램프에 이 가정이 상수로 박혀 있다.

```js
// src/voxel-map.js:48
const colorT = Math.min(1, Math.max(0, (center[1] + 1) / 3));
//                                       y=-1 -> 0,  y=+2 -> 1
//                                       "폰 높이 아래 1m가 바닥, 위 2m가 천장"
```

**② 운영자 뷰의 격자는 바닥이 아니다.** `GridHelper`(`src/operator-view.js:19`)는 y=0
평면에 그려지므로 **시작 시 폰 높이의 평면**이다. 복원된 방의 진짜 바닥은 그보다 1m쯤 아래에
나타난다. 처음 보면 "방이 격자 밑에 있다"고 오해하기 쉽다.

**③ 원점은 영원히 고정이 아니다.** ARCore는 이전에 본 장소를 다시 인식할 때
(loop closure, 루프 폐쇄) 누적 오차를 되돌려 좌표계 전체를 미세 보정한다.

```
[시작] 원점 확정  ->  [30초 후] ARCore: "추정이 8cm 틀렸었다" -> 좌표계 보정
                                 -> 저장해둔 (1.2, 0.4, -2.8) 은
                                    이제 현실의 그 지점을 안 가리킴 (X)
```

그래서 **"좌표를 숫자로 저장하는 것"과 "현실의 지점을 등록하는 것"은 다른 일**이다.
전자는 스냅샷, 후자는 갱신을 계속 받는 구독이다. 해법이 `XRAnchor`이며 4-8 ①에서 다룬다.

### 2-3. 투영 / 역투영 — 누가 무엇을 하나

가장 헷갈리는 지점. **투영은 두 군데에서 저절로 일어나고, 역투영은 우리만 한다.**

```
   현실 세계                   [폰 화면]                   가상 세계
   (방, 손, 책상)                                          (Ninja)

        *                          |                          *
         \   (1) 투영              |            (2) 투영     /
          \  (폰 렌즈 · 물리)      |       (three.js + GPU)  /
           \---------------------->|<----------------------/
                                   |
                            +------+------+
                            | (3) 역투영   |
                            |  (우리 코드) |
                            +------+------+
                                   |
                                   v
                       깊이 픽셀 -> 3D 좌표 -> 복셀 지도 / 가림막
```

| 일 | 담당 | 코드 위치 | 주기 |
|---|---|---|---|
| 현실 빛 → 카메라 영상 | 폰 렌즈 (물리) | 없음 | 항상 |
| 영상들 → 깊이맵 | ARCore | 없음 (API로 수신) | 매 프레임 |
| **깊이맵 → 3D 좌표 (역투영)** | **이 저장소 코드** | `src/depth-math.js:25` | 초당 5~15회 |
| Ninja 3D → 화면 (투영) | three.js + GPU | `src/main.js:307` 한 줄 | 초당 60회 |

**우리가 직접 쓰는 것은 역투영 하나뿐이다.** 나머지는 렌즈와 GPU가 해준다.

#### AR이 성립하는 이유 — 같은 행렬을 양쪽이 나눠 쓴다

실제 카메라와 가상 카메라의 투영이 어긋나면, Ninja가 책상 위에 있어도 화면에서는
엉뚱한 곳에 붙어 보인다. 그래서 WebXR이 **실제 카메라의 투영 행렬을 알려주고**, 그것을
두 곳에서 반대 방향으로 쓴다.

```
        WebXR이 준 projectionMatrix
                    |
        +-----------+-----------+
        v                       v
   그대로 곱한다            뒤집어서 곱한다 (.invert())
   three.js가 Ninja를       우리 코드가 깊이를
   화면에 그림 = (2) 투영    3D로 되돌림 = (3) 역투영
```

일반적인 컴퓨터비전이라면 체커보드로 카메라 보정(calibration)을 해야 하지만,
AR 런타임이 보정된 투영 행렬을 이미 넘겨주므로 그 과정이 생략된다.

#### 왜 굳이 역투영이 필요한가 (화면은 GPU가 그려주는데)

화면에 그리는 것 말고도 **현실 물체가 방 어디에 있는지를 숫자로 알아야** 하는 일이 있다.

| 용도 | 코드 |
|---|---|
| 방의 3D 복셀 지도 | `src/voxel-map.js` |
| 현실 모양의 보이지 않는 가림막 | `src/cpu-depth-occluder.js` |
| 운영자 뷰에서 위에서 내려다보기 | `src/operator-view.js` |

### 2-4. 한 프레임을 숫자로 따라가기 (발표 핵심)

> 아래 숫자는 **대표 예시값**이며 실기기에서 캡처한 측정치가 아니다.
> 단, **어떤 항목이 오는지 · 단위 · 배열 크기**는 코드와 WebXR 사양에 정해진 그대로다.

#### T0 — 페이지 접속

숫자는 오가지 않는다. 지원 여부만 묻는다.

```js
// src/main.js:125-126
navigator.xr.isSessionSupported('immersive-ar')   //  -> true
```

#### T1 — START AR

**보내는 것 (요청서)**

```js
// src/main.js:187-197
{
  requiredFeatures: ['hit-test'],
  optionalFeatures: ['anchors', 'dom-overlay', 'local-floor', 'depth-sensing'],
  depthSensing: {
    usagePreference:      ['cpu-optimized'],
    dataFormatPreference: ['luminance-alpha', 'float32'],
  },
}
```

**받는 것 (승인서)**

```
session.depthUsage      = "cpu-optimized"
session.depthDataFormat = "luminance-alpha"
```

> 4-6의 진단 문제는 **이 응답이 비어서** 생긴 것이다. 요청은 했으나 브라우저가 주지 않았다.
> HUD의 `depth usage` / `depth format` 표시가 바로 이 두 값이다.

#### T2 — 세션 시작, 원점 확정

`requestReferenceSpace('local')` 이 반환되는 순간 (0,0,0)이 확정된다. 첫 프레임의 포즈는

```
position    = { x: 0.000, y: 0.000, z: 0.000 }
orientation = { x: 0, y: 0, z: 0, w: 1 }
```

자기 자신이 원점이므로 당연하다.

#### T3 — 2초 후, 폰을 들고 이동한 상태에서 받는 재료 3개

세 재료가 실제로 한곳에 모이는 코드는 5줄이다.

```js
// src/depth-cloud.js:66-70
for (const { view, depthInformation } of snapshot.views) {
  this.inverseProjection.fromArray(view.projectionMatrix).invert();  // (2) 투영 행렬
  const invProjectionArray = this.inverseProjection.elements;
  const viewMatrix = view.transform.matrix;                          // (1) 카메라 포즈
  this.sampleView(depthInformation, invProjectionArray, viewMatrix); // (3) 깊이맵
}
```

**① 카메라 포즈** — `frame.getViewerPose(localSpace)`

```
position    = { x: 0.300, y: 0.050, z: -0.800 }
orientation = { x: 0.0000, y: 0.2588, z: 0.0000, w: 0.9659 }
```

| 값 | 의미 |
|---|---|
| `x: 0.300` | 시작점에서 오른쪽 30cm |
| `y: 0.050` | 시작할 때보다 5cm 높음 |
| `z: -0.800` | 앞으로 80cm (−Z가 앞) |
| 쿼터니언 | `sin(θ/2)=0.2588` → **+Y축 기준 30° 회전 = 왼쪽으로 30°** |

> 회전 방향 확인: `R_y(30°)`를 카메라 시선 `(0,0,-1)`에 적용하면 `(-sin30, 0, -cos30)`,
> 즉 `-X`쪽으로 기운다. `-X`는 시작 기준 왼쪽이므로 **왼쪽 30°** 회전이다.

같은 정보를 4×4 행렬로도 준다 (`view.transform.matrix`, column-major 16개).

```js
[ 0.8660,  0.0000, -0.5000,  0.0000,    // 1열: 카메라의 오른쪽 방향
  0.0000,  1.0000,  0.0000,  0.0000,    // 2열: 카메라의 위 방향
  0.5000,  0.0000,  0.8660,  0.0000,    // 3열: 카메라의 뒤 방향
  0.3000,  0.0500, -0.8000,  1.0000 ]   // 4열: 카메라 위치 (인덱스 12,13,14)
```

**② 투영 행렬** — `view.projectionMatrix` (세션 내내 거의 불변)

```js
[ 2.8563,  0.0000,  0.0000,  0.0000,
  0.0000,  1.4281,  0.0000,  0.0000,
  0.0000,  0.0000, -1.0004, -1.0000,
  0.0000,  0.0000, -0.0200,  0.0000 ]
```

| 위치 | 값 | 의미 |
|---|---|---|
| `[0]` | 2.8563 | 가로 화각 `2·atan(1/2.8563)` ≈ **39°** |
| `[5]` | 1.4281 | 세로 화각 `2·atan(1/1.4281)` ≈ **70°** |
| `[10]`,`[14]` | −1.0004, −0.02 | near = 0.01m, far = 50m |

**③ 깊이맵** — `frame.getDepthInformation(view)`

```
width            = 160                  // 카메라 영상보다 훨씬 작다
height           = 120
rawValueToMeters = 0.001                // 원본값 x 이 수 = 미터
data             = Uint16Array(19200)   // 160 x 120

data[9700] = 2400  ->  2.400 m
data[9701] = 2415  ->  2.415 m
data[9702] =    0  ->  0 = "여기는 깊이를 못 구했음"
```

`luminance-alpha` 포맷은 밀리미터를 uint16으로 담으므로 `rawValueToMeters = 0.001`이다.
프레임당 약 38KB. 다만 코드는 이 배열을 직접 인덱싱하지 않고 `getDepthInMeters(u, v)`를
쓰므로, 깊이 버퍼 ↔ 화면 사이의 회전/해상도 변환은 브라우저가 처리한다.

#### T4 — 역투영 (`src/depth-math.js:25-45`)

**입력**

```
u     = 0.75      // 화면 가로 75% 지점
v     = 0.30      // 화면 세로 30% 지점 (위쪽)
depth = 2.400 m   // getDepthInMeters(0.75, 0.30)
```

**1단계 · 이미지 좌표 → NDC**

```js
const xNdc = u * 2 - 1;          // 0.75 x 2 - 1 = 0.500
const yNdc = (1 - v) * 2 - 1;    // (1 - 0.30) x 2 - 1 = 0.400
```

이미지 좌표는 좌상단 원점이라 v가 아래로 증가하고, NDC는 y가 위로 증가한다.
**`1 - v` 뒤집기를 빼면 복원된 방이 상하로 뒤집힌다.**

**2단계 · 광선 방향 뽑기 (투영 행렬 뒤집기)**

```js
const ray = multiplyMat4Vec4(invProjection, [0.5, 0.4, -1, 1]);
//   -> [0.0017505, 0.0028009, -0.01, 1]      near 평면(1cm) 위의 점
const vx = ray[0] / ray[3];   // <- 원근 나눗셈(perspective divide)의 역
```

`w`(= `ray[3]`)는 "나중에 나눌 숫자"를 담아둔 4번째 칸이며 그 값은 거의 항상
**카메라로부터의 거리**다. 투영에서 `÷w`가 원근감을 만들고, 역투영에서 같은 나눗셈을 되돌린다.

**3단계 · 깊이만큼 늘리기 — 가장 미묘한 한 줄**

```js
const scale = depth / -vz;    // 2.400 / 0.01 = 240
// (0.0017505, 0.0028009, -0.01) x 240  ->  (0.42012, 0.67222, -2.400)
```

| 카메라 기준 좌표 | 의미 |
|---|---|
| x = 0.420 | 카메라 기준 오른쪽 42cm |
| y = 0.672 | 위로 67cm |
| z = −2.400 | 앞으로 2.4m — 깊이와 정확히 일치 |

> ⚠️ **깊이의 정의가 두 가지**라는 점이 함정이다.
>
> | 정의 | 의미 | 스케일 |
> |---|---|---|
> | ray distance (radial) | 광학중심에서 점까지 **직선거리** | `depth / 광선길이` |
> | **z-distance (perpendicular)** | 광축(−Z)에 **수직 투영한 거리** | **`depth / -vz`** ← ARCore |
>
> ARCore/WebXR `getDepthInMeters`는 **수직거리** 규약이므로 `-vz`로 나눈다.
> 혼동하면 화면 중앙에서는 두 값이 같아 **버그가 보이지 않다가**, 가장자리로 갈수록
> 오차가 커져 **평평한 벽이 그릇처럼 볼록하게 복원된다** (FOV 35° 지점에서 약 22% 오차).

검산: `2.8563 x 0.42012 / 2.400 = 0.500` → xNdc와 일치.

**4단계 · 방 기준으로 옮기기 (카메라 포즈 곱하기)**

```js
const world = multiplyMat4Vec4(viewMatrix, [0.42012, 0.67222, -2.40, 1]);

Xw = 0.8660 x 0.42012 + 0.5 x (-2.40) + 0.300  =  0.364 - 1.200 + 0.300 = -0.536
Yw = 1.0000 x 0.67222 + 0.050                  =  0.722
Zw = -0.5 x 0.42012 + 0.8660 x (-2.40) - 0.800 = -0.210 - 2.078 - 0.800 = -3.088
```

```
월드 좌표 = ( -0.536,  0.722,  -3.088 )
          시작점 기준 왼쪽 54cm, 위로 72cm, 앞으로 3.09m
```

> 카메라 기준으로는 **오른쪽**(camX=+0.42)이었는데 방 기준으로는 **왼쪽**(x=−0.54)이다.
> 폰이 왼쪽으로 30° 돌아 있어서 **정면 2.4m 지점 자체가 방 기준으로는 왼쪽**이기 때문이다.
> 지배적인 항은 오른쪽 오프셋(+0.364)이 아니라 전방 거리 성분(−1.200)이다.
> 이것이 재료 ①(카메라 포즈)이 하는 일이다.

한 식으로 쓰면:

```
p_world = T(view->world) · (depth / -v_z) · P^-1( [2u-1, 1-2v, -1] )
```

#### T5 — 복셀 지도에 등록 (`src/voxel-map.js`)

```js
const key = voxelKey(-0.536, 0.722, -3.088, 0.05);

x: -0.536 / 0.05 = -10.72  ->  floor  ->  -11
y:  0.722 / 0.05 =  14.44  ->  floor  ->   14
z: -3.088 / 0.05 = -61.77  ->  floor  ->  -62

key = "-11,14,-62"
```

관측 횟수 누적 (`VOXEL_SOLID_MIN_HITS = 3`):

| 시각 | 상황 | counts | solid? |
|---|---|---|---|
| 0.0초 | 첫 관측 | `"-11,14,-62" -> 1` | 보류 |
| 0.4초 | 다른 각도에서 재관측 | `-> 2` | 보류 |
| 0.9초 | 세 번째 | `-> 3` | **승격** |

```js
center = [ -0.525, 0.725, -3.075 ]      // (floor + 0.5) x 0.05
colorT = (0.725 + 1) / 3 = 0.575
R = 0.2 + 0.8 x 0.575 = 0.66
G = 0.5
B = 1.0 - 0.8 x 0.575 = 0.54
```

이 시점에 HUD의 `복셀 N`이 1 증가한다. **3회 관측 규칙이 이 프로젝트의 유일한 노이즈
필터**이며, TSDF(Truncated Signed Distance Function) 융합의 대폭 단순화된 형태다.
서로 다른 시점에서 같은 5cm 칸이 3번 맞아야 통과하므로 일회성 depth 노이즈가 걸러진다.

### 2-5. 전체 흐름과 처리량

```
 [폰 렌즈]      카메라 영상 (코드 밖)
      |
 [ARCore]      +----------------------------------------+
      |        | (1) 포즈    16개 숫자   (매 프레임)      |
 [브라우저]     | (2) 투영    16개 숫자   (거의 고정)      |
      |        | (3) 깊이  19,200개 값   (매 프레임)      |
 [우리 코드]    +----------------------------------------+
      |
   격자 샘플링 (40x30 또는 80x60)
      |
   역투영  u,v,depth -> (-0.536, 0.722, -3.088)
      |
   복셀 키 "-11,14,-62" -> 3회 관측 시 solid -> HUD 복셀 +1
```

| 항목 | 격자 | 주기 | 초당 역투영 횟수 |
|---|---|---|---|
| 복셀 지도 (`DepthCloud`) | 40 × 30 = 1,200 | 200ms (5Hz) | **6,000** |
| 동적 가림막 (`CpuDepthOccluder`) | 80 × 60 = 4,800 | 66ms (15Hz) | **72,000** |
| 화면 렌더 | — | 16ms (60Hz) | — |

데이터 크기의 **비대칭**이 최적화 방향을 결정한다. 포즈·투영은 각 16개 숫자인데 깊이맵은
19,200개다. 그래서 최적화가 전부 깊이 쪽에 몰려 있다 — 격자 샘플링(19,200개 중 1,200개만
읽음), 갱신 주기 제한, 배열·GPU 버퍼 재사용, 프레임 단위 캐시(4-8 ③).

병목은 렌더링이 아니라 `getDepthInMeters()`를 초당 수만 번 호출하는 **JS 루프**다.
가림막이 15Hz로 제한된 이유이며, 삼각형 9,322개는 모바일 GPU에 거의 부담이 아니다.

| 오해 | 사실 |
|---|---|
| "폰이 레이저를 쏴서 깊이를 잰다" | 광선은 수학적 직선이다. 깊이는 폰이 **움직이며** 생기는 시차를 삼각측량해 얻는다 (depth-from-motion). ToF 센서가 있는 기기도 있지만 API는 동일하다 |

## 4. 개발 기록 — 단계별 상세

### 4-1. [1단계] 단일 파일 프로토타입 → ES 모듈 분리

**상황** — 최초 프로토타입은 `index.html` 한 파일 615줄이었다. WebXR 세션, 게임 규칙,
렌더링, HUD가 전부 한 스크립트에 섞여 있었다.

**왜 이렇게 했나** — WebXR은 **실기기가 없으면 실행조차 되지 않는다.** 폰을 꺼내야만
확인할 수 있는 코드의 비율을 줄이는 것이 이후 모든 작업의 속도를 좌우한다고 판단했다.
그래서 "PC에서 검증 가능한 부분"과 "폰이 있어야 하는 부분"을 파일 경계로 갈랐다.

**문제** — 거리·각도 판정, 후보 랭킹 같은 순수 계산이 three.js 객체와 얽혀 있어
단독 실행이 불가능했다.

**해결** — 두 계층으로 분리했다.

- **순수 로직** (`game-rules.js`, `spatial-mapper.js`): three.js·DOM·WebXR을 import하지 않음
- **연동 계층** (`xr-session.js`, `ninja-model.js`, `main.js`): 브라우저 API 담당

**결과** — Node의 내장 테스트 러너만으로 게임 규칙을 검증할 수 있게 됐다.
`package.json`도 의존성 설치도 없이 `node --test tests/*.test.mjs`가 돈다.
이 구조는 이후 모든 단계에서 그대로 반복된다.

---

### 4-2. [2단계] 실세계 가림 1차 — GPU depth-sensing

**상황** — Ninja가 손이나 기둥 **뒤에** 있어도 항상 화면 위에 그려졌다.

**왜 이렇게 했나** — WebGL은 카메라 영상만 보고는 손이 Ninja보다 가까운지 알 수 없다.
현실 물체의 거리가 **렌더러의 깊이 버퍼에 들어와야** 앞뒤 판정이 가능하다.
three.js는 `depth-sensing`(`gpu-optimized`)이 활성화되면 전체화면 depth 메시를 자동으로
만들어 주므로, 그것을 가져다 쓰는 것이 가장 적은 코드로 가능한 방법이었다.

**해결** — 그 메시를 **깊이 전용**으로 바꿨다.

- `colorWrite = false` — 색은 칠하지 않고 깊이만 기록
- `renderOrder = -1` — Ninja보다 먼저 그려 깊이 버퍼를 채움

이렇게 하면 "Ninja가 가려졌는지"를 JavaScript로 계산할 필요가 없다. **GPU의 depth test가
픽셀 단위로 알아서 버린다.** 부분 가림도 공짜로 얻는다.

**결과** — 코드 3줄 수준으로 동적 가림이 배선됐고, depth 미지원 기기에서는 자동으로
비활성화되어 게임은 그대로 동작한다(graceful fallback).
⚠️ 다만 **이 기능이 갤럭시에서 동작하지 않는다는 사실은 6단계에서야 밝혀진다.**

---

### 4-3. [3단계] 스캔 점 시각화

**상황** — 20초 스캔이 실제로 무엇을 수집하는지 화면에 아무 흔적이 없었다.

**왜 이렇게 했나** — 스캔은 방 전체를 훑는 것이 아니라 **화면 중앙 광선(hit-test)이 맞은
점만** 성기게 줍는다. 이 동작이 보이지 않으면 "왜 후보가 이렇게 적지?"를 추측으로만
판단하게 된다. 디버깅 가능성을 위해 데이터를 화면에 드러냈다.

**해결** — 저장되는 후보마다 AR 씬에 구슬 마커를 찍는다.

- 🟢 초록 = 수평면(법선 y > 0.62, 닌자를 숨길 수 있는 곳)
- 🟠 주황 = 그 외 표면 점
- `depthTest: false`로 항상 앞에 그려 전체 분포가 보이게 함

**결과** — "20초를 스캔해도 점이 수십 개뿐"이라는 사실이 눈으로 확인된다.
수집 규칙(0.25초 간격, 22cm 이상 간격)의 효과를 직접 볼 수 있다.

---

### 4-4. [4단계] 3D 공간 복원 — 포인트클라우드 (`?depth=cloud`)

**상황** — 이 프로젝트의 컴퓨터비전 핵심. 깊이맵을 실제 3D 좌표로 펴야 한다.

**왜 이렇게 했나** — 가림(2단계)은 GPU에 맡기면 되지만, **"방을 3D로 복원했다"고 말하려면
좌표를 우리 손으로 계산해야 한다.** 그리고 그 계산이 맞는지 검증할 수 있어야 한다.

**해결** — 역투영(unprojection)을 순수 함수로 구현했다 (`depth-math.js`).

1. 정규화 뷰 좌표 (u, v) → NDC로 변환 (v축은 뒤집는다 — 이미지 원점은 좌상단, NDC는 y가 위)
2. 투영행렬의 역행렬로 카메라 광선을 복원
3. 광선의 **수직거리(view-Z)** 가 측정 깊이와 같아지도록 스케일 (ARCore 규약)
4. 뷰 행렬로 월드 좌표로 변환

**결과** — 초기에 원시 점을 그대로 렌더링해 확인한 결과, **상단 벽=분홍, 하단 바닥=파랑**으로
높이 구조가 일관되게 나왔다. 역투영이 정상 동작함을 육안으로 확인.
⚠️ 미터 단위 정확도(실제 표면에 정확히 붙는지)는 시차(parallax) 테스트로 추가 확인 필요.

### 4-5. [5단계] 복셀 재구성 + 운영자(서버) 3D 뷰

**상황** — 원시 포인트클라우드는 노이즈가 많고, 게임 화면에 그리면 지저분했다.

**왜 이렇게 했나 (노이즈 필터)** — 단일 프레임의 깊이는 오차가 크다. 한 번 반짝 나타난
점은 유령일 수 있다. 그래서 **"같은 5cm 칸을 3번 이상 관측했을 때만 solid로 승격"**
시킨다. 관측이 반복됐다는 사실 자체를 신뢰도로 쓰는, 시간적 누적 필터다.

**왜 이렇게 했나 (별도 화면)** — 게임 화면에 복원 결과를 겹치면 둘 다 못 보게 된다.
AR 세션은 유지한 채 **두 번째 3D 씬**을 별도 캔버스에 띄우는 방식을 택했다.

**문제** — 초기에는 게임 화면에 원시 점을 직접 그렸는데, 화면이 지저분해 플레이가 불가능했다.

**해결** — 게임 화면에서는 점을 **그리지 않고 데이터만 누적**하고, 시각화는 운영자 뷰에
맡겼다. 운영자 뷰에는 다음이 표시된다.

- 🧊 복원된 복셀 공간 (`InstancedMesh` 한 개로 최대 2만 개)
- 🔴 Ninja가 실제로 숨은 위치 (게임 화면에서는 안 보이는 정보)
- 🔵 플레이어 이동 경로 (15cm 이상 움직였을 때만 기록)

**결과** — "복원된 3D 공간이 실제 방과 맞는가"를 폰 화면에서 바로 검증할 수 있게 됐다.

### 4-6. [6단계] 🔍 진단 — 갤럭시가 GPU depth를 주지 않는다

**상황** — 2단계에서 만든 가림이 갤럭시 S26 Ultra에서 **전혀 동작하지 않았다.**
Ninja는 여전히 손을 뚫고 보였다.

**왜 이렇게 했나** — 원인 후보가 여러 개였다. ① 폰이 깊이를 못 만든다 ② 브라우저가 기능을
안 준다 ③ 우리 코드 배선이 틀렸다. **추측으로 고치면 셋 다 건드리게 되므로**, 먼저 어느
계층에서 끊겼는지 드러내는 계측을 넣었다.

**해결** — HUD에 WebXR 세션의 실제 값을 그대로 노출했다.

```
depth usage   cpu-optimized / gpu-optimized / unavailable
depth format  luminance-alpha / float32 / -
```

**진단 결과** — 갤럭시 기본 URL에서 `depth usage unavailable`이 표시됐다.
그런데 `?depth=cloud`(cpu-optimized 요청)에서는 **수만 개의 점이 정상 생성**됐다.

> 즉 **폰의 깊이 계산은 동작한다. 브라우저가 GPU 전달 방식만 세션에 제공하지 않았다.**

**결과** — 원인이 ②로 특정됐다. 폰이나 우리 코드를 고칠 문제가 아니라, **브라우저가
자동으로 해주지 않는 일을 애플리케이션이 직접 해야 하는 문제**로 성격이 바뀌었다.

### 4-7. [7단계] CPU depth로 가림막을 직접 만들다 (`?occlusion=cpu`)

**상황** — GPU 경로가 막혔지만 CPU 경로로는 깊이가 온다. 그 깊이로 가림을 직접 구현한다.

**왜 이렇게 했나 (누적 데이터를 안 쓴 이유)** — 이미 `?depth=cloud`가 점을 쌓고 있으니
그걸 쓰면 될 것 같지만, **그건 누적 지도다.** 이미 지나간 손의 위치까지 남아 있어
움직이는 손을 가리는 데는 맞지 않는다. 동적 가림에는 **최신 깊이만** 필요하다.

**해결** — 깊이맵을 `80 × 60` 격자로 샘플해 매 프레임 삼각형 메시를 새로 만든다.

| 장치 | 값 | 이유 |
|---|---|---|
| 격자 | 80 × 60 (삼각형 최대 9,322개) | 해상도와 모바일 부하의 절충 |
| 색 | `colorWrite: false` | 깊이만 기록, 화면엔 안 보이는 가림막 |
| 삼각형 끊기 | 깊이 차 20cm 초과 시 연결 안 함 | 손 가장자리와 먼 벽을 이어 화면이 통째로 가려지는 것 방지 |
| depth bias | 5cm | 표면 위의 Ninja가 깊이 오차로 통째로 잘리는 것 방지 |
| 갱신 주기 | 66ms (약 15Hz) | 폰 부하 제한, 배열·GPU 버퍼 재사용 |
| stale 처리 | 250ms 무입력 시 숨김 | 낡은 가림막이 화면에 남는 것 방지 |

**결과** — 브라우저가 안 해주는 일을 애플리케이션이 대신하는 경로가 생겼다.
HUD의 `가림 CPU · 삼각형 N`으로 메시가 실제 생성되는지 확인할 수 있다.
⚠️ 실기기에서의 가림 **품질**은 아직 검증 대상이다.

### 4-8. [8단계] 통합 — 앵커 · 표면 분리 · depth 공유 · 장시간 안정성

이 단계에서는 서로 다른 네 가지 문제를 함께 해결했다. 설계 문서:
`docs/superpowers/specs/2026-08-25-anchor-shared-cpu-depth-design.md`

#### ① Ninja 위치가 실제로 고정되어 있지 않았다

**문제** — 코드에 `anchor` 필드와 anchor pose를 읽는 로직은 있었지만, **정작
`XRAnchor`를 생성하지 않았다.** 실상은 local 좌표 한 점을 저장한 것에 가까웠다.
ARCore가 나중에 공간 이해를 보정해도 Ninja는 따라가지 않는다.

**해결** — 활성 `XRFrame`에서 `createAnchor()`를 호출한다. WebXR anchor 생성은 활성
frame 안에서만 허용되므로, 버튼 클릭(=비활성 frame) 시점에는 위치만 계산해 두고 다음
frame에서 생성한다. 이후 매 frame `anchorSpace`의 최신 pose를 읽어 렌더 행렬과 탐지
좌표를 함께 갱신한다. 미지원·실패 시 local 좌표로 fallback하며 게임은 계속된다.

> **왜 복셀 지도로는 위치를 고정할 수 없나?** 복셀 지도는 깊이 점을 칸에 누적한
> **시각화·분석 데이터**일 뿐, 그 칸을 WebXR 추적 시스템의 현실 지점으로 **등록**하지
> 않는다. 점이 아무리 많아져도 Ninja 좌표가 보정되지 않는다. 역할이 다르다.

#### ② Ninja가 배치 표면에 파묻혔다

**문제** — 기존에는 선택 지점에서 Y축으로만 살짝 올렸다. **벽 같은 수직면에서는 Y축
이동이 표면에서 떼어놓지 못한다.** Ninja와 벽의 깊이가 거의 같아져, 깊이 오차와 bias
때문에 머리나 몸 전체가 잘렸다.

**해결** — 전역 depth bias를 키우는 대신(그러면 손 가림 정밀도가 망가진다),
**표면의 normal 방향으로 필요한 만큼만** 떼어놓는다. 바닥·책상은 2cm, 벽·경사면은
카메라 쪽으로 12cm. 계산된 최종 좌표 하나를 렌더링과 SCAN 판정에 함께 써서
**보이는 위치와 게임이 탐지하는 위치가 어긋나지 않게** 했다.

#### ③ 같은 깊이를 두 번 읽고 있었다

**문제** — `CpuDepthOccluder`와 `DepthCloud`가 각각 `getDepthInformation()`을 호출했다.
두 기능을 동시에 켜면 같은 프레임의 깊이를 중복 조회한다.

**해결** — `CpuDepthFrameSource`가 **현재 `XRFrame`을 열쇠로** 조회 결과를 캐시한다.
같은 frame에서 두 번째 소비자는 캐시된 snapshot을 받는다. 갱신 주기는 각자 독립이다
(가림 15Hz / 지도 5Hz). 이 변경으로 **"한 세션에 한 실험만"이라는 제약이 풀렸고**,
`?occlusion=cpu` 하나에서 가림과 공간지도를 동시에 쓸 수 있게 됐다.

#### ④ 장시간 실행 시 메모리가 계속 늘었다

**문제** — 한두 번만 관측된 depth 노이즈의 카운트가 Map에 무한히 쌓였다.

**해결** — 미확정 복셀을 최대 40,000개로 제한하고 오래된 항목부터 교체한다. solid가 된
복셀은 카운트에서 제거하고, solid가 상한(2만)에 도달하면 카운트를 더 쌓지 않는다.
추가로 지도 revision을 도입해 **복셀 GPU 버퍼는 실제로 바뀌었을 때만** 다시 올린다.

### 4-9. [9단계] 숨는 대상을 하츄핑 3D 스캔 모델로 교체

**상황** — 지금까지 숨는 대상은 코드로 조립한 닌자(캡슐·구·원뿔)였다.
이를 `hcp.glb`(하츄핑을 3D 스캔한 모델)로 바꾼다.

**모델 실측**

| 항목 | 값 |
|---|---|
| 생성 도구 | `trimesh` (파이썬) |
| 원본 크기 | 1.02 × 0.99 × 0.68 m |
| 삼각형 / 정점 | 186,117개 / 93,181개 |
| 재질 | **없음**. 텍스처 없음, 정점 색상(COLOR_0)만 존재 |
| 파일 크기 | 3.7MB |

**문제 세 가지와 해결**

| 문제 | 원인 | 해결 |
|---|---|---|
| 로딩 방식 불일치 | `createNinja()`는 동기인데 GLB는 다운로드가 필요 | 앱 시작 시 한 번 로드해 **템플릿**으로 두고, 라운드마다 `clone()` |
| 바닥에 파묻힘 | 닌자는 발바닥이 원점, GLB는 **한가운데가 원점** | 경계 상자로 높이 0.5m 스케일 + 바닥을 y=0에 맞추는 오프셋 |
| 위장 투명도가 안 먹힘 | `clone()`은 재질을 **참조로 공유** | 인스턴스마다 재질을 복제한 뒤 투명도 설정 |

**왜 Group으로 한 겹 감쌌나** — `NinjaGame`은 받은 객체의 `position`과 `quaternion`에
직접 값을 쓴다. 크기 보정을 그 객체에 넣으면 게임이 위치를 쓰는 순간 덮어씌워진다.
**바깥 껍데기는 게임이 움직이고, 안쪽 노드가 보정을 들고 있는** 구조로 분리했다.

**결과** — GLB 로드에 실패해도 기존 닌자로 폴백하므로 세션이 죽지 않는다.
실기기 현장에서 3.7MB 다운로드는 얼마든지 실패할 수 있다는 판단이다.

### 4-10. [10단계] 🎨 색이 검게 나오는 문제

**상황** — 폰에서 확인하니 하츄핑이 원본의 분홍색으로 보이지 않았다.

**진단** — 두 가지 원인이 겹쳐 있었다.

**원인 ① — 재질 기본값이 "완전 금속"**

`hcp.glb`에는 재질 정의가 아예 없다. 이때 GLTFLoader는 glTF 규격의 기본값으로 재질을
만드는데, 그 기본값이 **`metalness = 1`(완전 금속)** 이다. 금속은 물리적으로 자기 색이
없고 주변 환경을 반사만 하는데, 이 씬에는 환경맵이 없다. **반사할 것이 없으니 거의
검게** 나온다. 정점에 색이 아무리 잘 박혀 있어도 화면에 나타나지 않는다.

**원인 ② — 색공간 불일치**

GLB에 박힌 실제 값을 추출해 확인했다.

```
평균 RGB (207, 142, 158)   ← 하츄핑의 분홍빛
샘플:    (191, 135, 138), (190, 137, 139), ...
```

`trimesh`는 이 값을 **화면용 sRGB 숫자 그대로** 넣었는데, **glTF 규격은 COLOR_0을
linear로 정의한다.** 규격을 지키는 렌더러일수록 이 값을 linear로 읽어 한 번 더 밝기
변환이 들어가고, 결과적으로 **색이 바래고 채도가 떨어진다.**

**해결**

1. 재질을 **`MeshBasicMaterial`(unlit)** 로 교체 — 포토그래메트리는 촬영 당시의 빛과
   그림자가 이미 색에 구워져 있다. 조명을 다시 입히지 않는 쪽이 원본에 충실하다.
2. 정점 색을 **sRGB → linear로 한 번 디코딩** — 템플릿에 한 번만 적용한다.
   정점이 93,181개라 라운드마다 변환하면 매번 37만 번의 거듭제곱 연산이 들어간다.

**검증 결과** — 실제 `GLTFLoader`로 로드해 왕복 확인했다.

```
vertex 0: 원본 GLB 바이트 191 135 138
  저장된 linear    0.52100 0.24228 0.25415
  다시 sRGB로      191 135 138          ← 정확히 일치
평균 표시 RGB      207.2, 142.2, 158.0  ← GLB 원본과 동일
```

### 4-11. [11단계] 하츄핑 도망 모드 + 지도뷰 (`private/jaehoon`)

**상황** — 지금까지 하츄핑은 한 곳에 숨어 있기만 했다. 복원한 공간을 실제로 *쓰는*
게임을 만들려면, 하츄핑이 **그 공간의 지형을 따라 도망다니고** 플레이어가 쫓아가
잡는 모드가 필요했다. 새 페이지 `v4-chase.html`로 얹었다(`?occlusion=cpu`가 자동으로 붙는다).

**핵심 문제** — 복셀 지도는 "여기 뭔가 있다"만 알려준다. 움직이려면 **"여기 설 수 있는가,
여기서 저기로 갈 수 있는가"** 를 알아야 한다.

**해결**

- **통행 격자(`traversal-grid.js`)** — 복셀을 위에서 내려다본 **20cm 바둑판**으로 다시 정리하고,
  각 칸의 높이를 10cm 두께 슬랩 64겹으로 기록한다. 한 칸이 바닥·탁자 위처럼 여러 높이를
  가질 수 있어 하츄핑이 가구 위로 오를 수 있다. 어떤 슬랩 위 50cm(몸 높이)가 비면 설 수 있다.
  복셀 하나가 확정될 때마다 그 칸만 갱신한다(전체 재구축 대비 **110배 빠름** 측정).
- **천장 문제** — 천장은 기하학적으로 탁자와 같다(얇은 층 + 위가 미관측). 1차 실기기 테스트에서
  하츄핑이 천장으로 올라가, **바닥 추정(8칸 이상이 공유하는 가장 낮은 슬랩) + 1.3m 상한**을 넣었다.
- **벽 윗면 문제** — 2m 벽의 윗면도 "설 수 있음"으로 판정되므로, 하츄핑의 현재 위치에서
  **flood fill로 실제 닿을 수 있는 칸만** 남긴다.
- **도망·잡기(`chase-path.js`, `chase-runner.js`, `capture-gauge.js`)** — 통행 가능한 칸 위에서
  경로를 짜 이동하고, 플레이어가 가까이 붙어 SCAN을 **누르고 있어야** 게이지가 차서 잡힌다.
- **부수 작업** — v3 지도뷰(`v3-mapview.html`), 카메라 위에 감지된 평면·앵커 오버레이,
  WebXR 기능 탐색 페이지, 인수인계 문서 2종(`chase-mode-handoff.md`,
  `webxr_hide_seek_development_handoff.md`).

**결과** — 갤럭시 S25 1차 실기기 플레이 테스트와 그에 따른 수정까지 완료. 테스트 89 → 152개.

### 4-12. [12단계] 키프레임 복셀 복원 + 진단 모드 (`private/baencho`)

**상황** — 도망 모드가 복셀 지도 위에서 돌기 시작하자, 그 지도가 **얼마나 믿을 만한지**가
게임 품질을 결정하게 됐다. 복원 결과를 실기기에서 눈으로 검증할 수단이 필요했다.

**진단 — 기존 누적기가 시점이 아니라 샘플을 세고 있었다**

`VoxelMap`의 "같은 칸을 3번 이상 관측하면 solid" 규칙은 **서로 다른 시점 3개**를 뜻해야 한다.
그런데 `depth-cloud.js`가 200ms마다 뿌리는 40×30 격자는 1m 거리에서 샘플 간격이 ~2.9cm인데
복셀 한 변은 5cm다. **한 프레임의 광선 여러 개가 같은 칸에 떨어져 임계값이 한 장으로 충족**된다.
간격은 거리에 비례하므로(4m에서 11.6cm) 가까운 것은 즉시 통과하고 먼 것만 걸러지는
**거리 의존 편향**이 생긴다. 화면에서는 "원거리 복원이 깨졌다"처럼 보이지만 필터의 결함이다.

**해결 — 별도 파이프라인 `?voxel=debug`** (기존 모드는 건드리지 않음)

- **키프레임만 캡처** — 직전 대비 **20cm 이동 또는 15° 회전**일 때만(최대 40장). 포즈 판정은
  매 프레임, 쿨다운은 캡처에만 걸어 임계값이 조용히 넓어지지 않게 한다.
- **프레임 단위 중복 제거(`voxel-grid.js`)** — 한 키프레임은 한 칸에 **최대 1표**. 이제 관측 횟수가
  "동의한 시점의 수"를 뜻한다.
- **이상치 2단계(`depth-grid-filter.js`)** — 유효 범위(0.3~5m) + 이웃 깊이 불연속 검사로
  물체 경계의 flying pixel 제거. 역투영은 ARCore가 광선 길이가 아니라 **광축 수직 거리**를
  주는 점을 반영한다.
- **원본 보존·재필터(`keyframe-store.js`)** — 스캔 중에는 깊이 격자와 포즈를 그대로 쌓고 복셀은
  시각화 시점에 계산한다. **슬라이더를 움직이면 재스캔 없이 같은 데이터로 재필터**되므로
  파라미터 효과를 같은 스캔 위에서 비교할 수 있다. JSON 내보내기/불러오기로 PC에서 반복 실험
  (`viewer.html`에 JSON을 드롭하면 폰 없이 같은 재필터·색상 모드·occluder 메시를 볼 수 있다).
- **시각화** — 관측 횟수(1=빨강/2=노랑/3+=초록)·높이·클러스터 색상 모드, 키프레임 카메라
  프러스텀(포즈 누적이 매끄러운 호인지), AR 화면 위 복셀 wireframe, 바닥 평면 추정.
- **정적 복셀 occluder 실험(`?occluder=voxel`)** — 9장의 "Phase 2"였던 것. 확정 복셀을 면 병합
  깊이 전용 메시로 만들어 캐릭터보다 먼저 그리면 z-test가 뒤쪽 픽셀을 버린다. 맞닿은 면 제거로
  삼각형 58~75% 감소, polygonOffset으로 발 잘림 방지. **실기기에서 체감 효과가 뚜렷하지 않아
  기본값은 꺼져 있고** URL 파라미터로만 켠다.
- **도망 모드 연결** — 키프레임 모드에서는 3회 이상 관측된 복셀만 통행 격자에 공급한다.
  같은 스캔에서 "관측됐지만 설 곳 없는 칸"이 57 → 12로 줄었다(허공 노이즈가 걸러진 결과).
  단, 이 경로는 `?voxel=debug`/`?occluder=voxel`에서만 쓰이며 기본 도망 모드는 기존 경로 그대로다.

**실기기 결과 (갤럭시)** — 1차: 키프레임 28장/18초 → 복셀 19,330개, 바닥과 0.70m 위 책상 높이에
히스토그램 봉우리, 카메라 높이 1.42m로 손에 든 폰과 일치. 2차: 거실 3.7분 → 복셀 61,990개(0.05m),
임계값 1→2→4 전환 시 61,990 → 21,265 → 6,145로 즉각 재필터, 검은 물체 주변의 시선 방향 번짐
아티팩트가 임계 4에서 사라짐. 재구성 249~717ms.

**되지 않은 것** — 바닥을 지우고 3D 연결 성분으로 물체를 나누는 기하 분할. 복원 결과가 부피가
아니라 표면 껍질이고 실내 가구가 서로 닿아 있어 84~96%가 한 덩어리로 남는다. 도망 모드가
물체를 나누는 대신 "설 수 있는가"만 묻는 쪽으로 간 것이 옳았다는 근거가 됐다.

**부수 수정** — 운영자 뷰 `InstancedMesh` 재질의 `vertexColors: true`를 제거. `BoxGeometry`에 색
속성이 없어 셰이더가 0을 곱해 **복셀과 도망 모드 통행 타일이 검게** 그려지던 버그로, 기본 모드에도
적용되는 유일한 동작 변경이다. 테스트 152 → 251개.

## 5. depth 모드

WebXR는 세션당 depth 모드를 하나만 쓸 수 있어, URL로 구분한다.

| | 기본 URL | `?occlusion=cpu` | `?depth=cloud` | `?voxel=debug` |
|---|---|---|---|---|
| depth usage | `gpu-optimized` | `cpu-optimized` | `cpu-optimized` | `cpu-optimized` |
| 하는 일 | three.js 내장 가림 | 동적 메시 가림 + 복셀 지도 | 복셀 공간 복원 진단 | 키프레임 복셀 진단 |
| 동적 손 가림 | 브라우저 지원 시 가능 | 가능, 실기기 검증 필요 | 불가(과거 점을 누적) | 불가(가림 전부 끔) |
| 운영자 뷰 | 없음 | 복셀·Ninja·anchor·이동 경로 | 같은 공간지도 진단 뷰 | 복셀·키프레임 프러스텀 |
| HUD 표시 | `가림 GPU` 또는 unavailable | `가림 CPU · 삼각형 N · 복셀 N` | `복셀 N` | 키프레임·히스토그램·폐기 통계 |
| 갤럭시 현재 결과 | GPU depth unavailable | 새 검증 대상 | CPU depth 정상 확인 | 1·2차 실기기 진단 완료 |

`?depth=cloud&occlusion=cpu`처럼 두 값을 동시에 넣으면 통합 CPU 게임 모드를 우선한다.
`?voxel=debug`는 그보다도 우선한다 — 가림이 살아 있으면 복셀 wireframe이 실물 뒤에서
깊이 테스트로 잘려나가, 정작 확인해야 할 "책상 반대편이 복셀화됐는가"를 볼 수 없다.

- `v4-chase.html` — 도망 모드 페이지. `?occlusion=cpu`를 자동으로 붙인다.
- `?occluder=voxel` — 정적 복셀 occluder(실험). depth 파이프라인과 별개 축이라 별도 파라미터이며,
  CPU 깊이가 필요하므로 실질 조합은 `?occlusion=cpu&occluder=voxel`이다.

## 7. 실행 / 테스트 방법

**기기 요건**: ARCore Depth 지원 Android + 최신 Chrome + HTTPS. (데스크톱은 미지원 안내 표시)

1. **갤럭시 CPU 가림 테스트**: `?occlusion=cpu` URL → START AR → HUD에서
   `depth usage cpu-optimized`와 `가림 CPU · 삼각형 N` 확인 → Ninja 앞에 책이나 상자를 둔 뒤
   손을 천천히 좌우로 움직여 가림 영역이 따라오는지 확인.
2. **GPU 가림 비교**: 기본 URL → START AR → `depth usage unavailable`이면 이 기기의 브라우저가
   GPU 방식을 제공하지 않는 것이므로 CPU 가림 URL과 결과를 비교한다.
3. **공간 복원 테스트**: `?depth=cloud` URL → START AR → 걸어다니며 방을 비추기 →
   HUD `복셀 N`이 늘어나는지 확인 → **`운영자 뷰`** 버튼으로 복원된 공간 확인.
4. **게임 플레이**: 20초 스캔 → Ninja 자동 숨김 → 걸어서 탐색 → 중앙 조준 후 SCAN → DETECTED!
5. **추적 안정성**: `기준점 저장` → 3~5m 이동/360° 회전 → 복귀 → `복귀 오차 확인`.

### 배포 후 Galaxy S26 Ultra 완료 조건

코드·Node 자동 테스트로 실기기 성공을 대신할 수 없다. 배포된 `?occlusion=cpu` 주소에서
직접 확인하고, 실패하면 HUD 전체와 화면을 캡처한다.

1. `depth usage cpu-optimized`와 실제 `depth format`이 표시된다.
2. Ninja를 숨기면 `고정 anchor`가 표시된다. `고정 local`이면 미지원 또는 생성 실패다.
3. 3~5m 이동하거나 방향을 바꿔도 Ninja가 같은 현실 위치에 유지된다.
4. 운영자 화면에서 `복셀 N`과 플레이어 이동 경로가 계속 증가한다.
5. 손이나 물건이 없을 때 Ninja의 머리와 몸 전체가 보인다.
6. 손이나 책을 Ninja 앞에 놓으면 겹친 부분만 가려진다.
7. 운영자 화면을 닫은 뒤에도 게임, anchor tracking, 복셀·경로 누적이 계속된다.
8. **하츄핑 모델이 원본 분홍색으로 표시된다** (발견 시 불투명 상태에서 확인).

`삼각형 0`이 계속되거나 depth usage가 unavailable이면 가림 품질 문제가 아니라 먼저
WebXR depth 세션 활성화 문제로 분류한다.

## 9. 미해결 과제 / 다음 단계

### 조사 중인 문제

- **20초 스캔 중 표면 마커가 보이지 않는다** — 3단계에서 구현한 초록/주황 마커가
  실기기에서 표시되지 않는다는 보고가 있다. 원인 후보: hit-test가 표면을 못 찾음
  (HUD `hit-test searching`), 22cm 간격 규칙에 걸림, 렌더 순서 문제. 다음 확인에서
  **HUD의 `표면후보 N` 숫자가 증가하는지**와 **`hit-test FOUND` 여부**를 먼저 본다.

- **SCAN 판정이 가림을 고려하지 않는다** — 현재 탐지는 거리(≤5m)와 각도(≤12°)만 본다.
  가림은 GPU의 픽셀 연산이라 CPU 쪽 게임 로직이 그 결과를 모른다. 따라서 **Ninja가
  기둥이나 벽 뒤에 완전히 가려져 있어도 방향만 맞으면 DETECTED가 뜬다.** 이를 맞추려면
  뷰어→Ninja 광선을 복셀 맵에 대고 쏘는 가시성 검사가 필요하다(재료는 이미 있다).

### 다음 단계

- **키프레임 복원을 기본 모드에 적용**: 12단계에서 확인한 "샘플을 세는" 결함은 진단 모드에서만
  고쳐져 있다. 기본 `VoxelMap`/도망 모드 지형 공급 경로에도 프레임 단위 중복 제거를 넣는다.
- **복셀 기반 정적 오클루전 (Phase 2)**: `?occluder=voxel`로 실험 구현은 됐으나 체감 효과가
  뚜렷하지 않았다. 메시가 방과 정렬됐는지 확인할 반투명 진단 표시부터 만들고 재검증한다.
- **재구성 속도**: 0.04m 복셀에서 717ms로 슬라이더가 버벅인다. 바뀐 부분만 갱신하거나 하한을 올린다.
- **Persistent/Cloud Anchor**: 현재 XRAnchor는 같은 세션 동안의 고정이 목적이다.
  세션 종료 후 같은 현실 위치를 복원하려면 Persistent 또는 Cloud Anchor가 필요하다.
  별도 저장 권한·API·식별자 수명·개인정보 설계가 필요해 이번 범위에서 제외했다.
- **매끄러운 메시**(마칭큐브 등): 성능 확인 후 복셀 다음 단계로.
- **MediaPipe 손동작 트리거**: SCAN 버튼을 `주먹→가위→주먹` 제스처로 대체.
- **모델 경량화**: 하츄핑 186,117 삼각형이 실기기에서 무거우면 감량 검토.

## 11. 제한 / 주의

- ARCore Depth 미지원 기기에서는 오클루전·포인트클라우드가 동작하지 않는다(게임은 정상).
- CPU 가림은 깊이 해상도와 약 15Hz 갱신률의 영향을 받으므로 빠른 손동작에서 가장자리가 늦게
  따라올 수 있다. 투명·반사 물체와 카메라에 아주 가까운 손은 ARCore 깊이 결손이 생길 수 있다.
- 오클루전/역투영의 실기기 기하 정확도는 아직 검증 중이다.
- 브라우저가 WebXR Anchors를 지원하거나 생성에 성공해야 `고정 anchor`가 된다. 미지원·거절 시
  `고정 local` fallback이므로 장거리 이동에서 드리프트가 더 보일 수 있다.
- 같은 세션의 XRAnchor도 ARCore 추적 품질의 영향을 받는다. 빠른 이동, 어두운 공간, 무늬 없는 벽,
  카메라 가림이 지속되면 `추적 일시 손실`이 생길 수 있으며 마지막 pose를 유지한 뒤 자동 복구한다.
- 앱 종료 후 같은 위치 복원은 이번 XRAnchor 범위가 아니며 Persistent/Cloud Anchor가 필요하다.
- 하츄핑 모델은 조명을 받지 않는 unlit으로 그려진다. 스캔 당시의 음영이 그대로 보이며,
  주변 조명에 따라 밝아지거나 그림자가 지지 않는다.
- 숨어 있는 동안 모델은 13% 투명이므로 색이 흐릿하다. 발견 시 불투명해진다.
- 아직 MediaPipe 손동작은 WebXR와 결합되지 않았고, SCAN 버튼이 그 자리를 대신한다.
