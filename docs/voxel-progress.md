# 복셀 오클루전 작업 노트

작성일: 2026-08-25
대상 브랜치: `private/baencho/better`
관련 문서: `voxel-occlusion-spec.md`(원본 명세), `docs/superpowers/specs/2026-08-25-voxel-debug-map-design.md`, `docs/superpowers/plans/2026-08-25-voxel-debug-map.md`

목표: **하츄핑이 실제 물체 뒤로 숨고 물체를 피해 이동하는 것.** 그 전제로 방의 형상을 담은 복셀 맵이 필요하고, 이 노트는 그 복셀 맵을 만들고 검증한 기록이다.

## 1. 무엇을 했나

### 1-1. 명세의 전제가 틀렸다는 것부터 확인

`voxel-occlusion-spec.md`의 Phase 0은 "복셀 맵 관련 구현은 현재 없음. 신규로 작성한다"고 적고 있었으나 **사실이 아니었다.** 이미 있던 것:

| 명세가 요구한 것 | 이미 있던 구현 |
|---|---|
| 복셀 누적 구조 | `src/voxel-map.js` — `floor(pos/size)` 키, 3회 승격, 테스트 7개 |
| InstancedMesh 디버그 렌더러 | `src/operator-view.js` — OrbitControls + 2만개 상한 + revision 게이트 |
| 역투영 | `src/depth-math.js:25` `depthSampleToWorld()` — three 비의존, 테스트됨 |
| depth 획득 | `src/cpu-depth-frame-source.js` — XRFrame 단위 캐시 |
| Phase 5 occluder 트릭 | `src/main.js`, `src/cpu-depth-occluder.js` 두 군데 |

따라서 명세가 지시한 `src/xr/`, `src/voxel/`, `src/debug/` 트리를 새로 만들지 않고 **기존 평면 구조를 확장**했다.

### 1-2. 진짜 결함을 찾았다

`src/depth-cloud.js:99`가 유일한 `voxelMap.observe()` 호출부인데 **frameId 개념이 없었다.** 40×30 격자를 ~60° 시야에 뿌리면 1m 거리에서 샘플 간격이 ~2.9cm, 복셀은 5cm — **한 프레임이 같은 칸에 2~3표를 넣어 즉시 solid로 승격**시킨다.

결정적으로 이 결함은 **거리 의존적**이다. 간격이 2m에서 5.8cm, 4m에서 11.6cm이므로 ~1.7m 너머는 실제로 여러 프레임이 필요하다. 결과적으로 **가까운 것은 초록, 먼 것은 빨강**인 맵이 나오는데, 이건 명세 Phase 2 진단표의 "다중 관측 검증이 작동 안 함" 증상과 구분이 불가능하다.

`VOXEL_SOLID_MIN_HITS = 3`이 "세 시점에서 봤다"를 전혀 보장하지 못하고 있었다.

### 1-3. 새 파이프라인 (`?voxel=debug`)

기존 `DepthCloud`/`VoxelMap`은 **한 줄도 바꾸지 않고** 기존 모드 전용으로 남긴 채, 별도 경로를 만들었다.

```
XRFrame + viewerPose
  → KeyframeGate.shouldCapture     매 프레임 평가 (~7 flops)
  → CpuDepthFrameSource.read       게이트 통과 시에만
  → KeyframeCapture                views[0]만, 네이티브 해상도
  → KeyframeStore                  원본 보존 (~1.2MB)
        ↓ 슬라이더 조작 시 재실행
  → rebuildVoxelGrid               범위클립 → 그래디언트 → 역투영 → 프레임중복제거
  → VoxelGrid                      observationCount + 누적 평균 좌표
  → selectCells(minObservations)   렌더 시점 필터, 재구성 없음
  → OperatorView / VoxelOverlay
```

핵심 설계 결정:

- **원본 보존.** 스캔 중에는 복셀 맵을 만들지 않고 키프레임 depth를 네이티브 해상도로 쌓아둔다. 복셀 맵은 시각화 시점에 계산하므로 **슬라이더를 움직이면 재스캔 없이 같은 데이터로 재필터**된다. 이게 없으면 파라미터를 바꿀 때마다 다른 스캔으로 실험하게 되어 비교 자체가 무의미해진다.
- **`.data` 미접근.** `getDepthInMeters(u,v)`만 써서 uint16/float32 포맷 분기 코드를 아예 만들지 않았다.
- **프레임 중복 제거는 `Set<frameId>`가 아니라 `lastFrameId`.** 명세는 셀마다 Set을 요구했지만 20만 셀에 Set을 달면 다시 읽지도 않을 정보에 ~20MB가 든다. 재구성이 키프레임을 순서대로 소진하므로 동치이며, 이 전제는 테스트로 고정했다.

### 1-4. 실기기 피드백 반영 (2회)

**1차 — 복셀이 전부 까맣게 보임.** `vertexColors: true`가 셰이더의 `USE_COLOR`를 켜서 `vColor *= color`를 실행하는데 `BoxGeometry`에 color 속성이 없어 `(0,0,0)`으로 읽혔다. `setColorAt`이 채운 색이 곱해지기 전에 0이 된다.

이건 이 저장소가 **2026-08-25 16:17에 이미 진단하고 고쳤던 버그**(커밋 `46d860d`)인데 HEAD의 revert들에 휩쓸려 되돌아왔고, 내가 그 패턴을 복사한 뒤 `voxel-overlay.js`에도 심었다. 둘 다 제거하고 이유를 주석으로 박았다.

**2차 — 40초 화면 녹화 프레임 분석.** 4가지 문제를 발견해 수정:

| 문제 | 수정 |
|---|---|
| 게임이 디버그 모드 밑에서 계속 돎 (`phase hunt`, `scan 19회/miss 19회`, 초록 마커 27개) | `autoStartsGame()` 게이트. 패널에 `게임 시작` 버튼으로 되돌릴 수 있게 |
| 운영자 뷰에서 상단 카드와 패널이 같은 텍스트 중복 | `formatVoxelDebugSummary()` 한 줄 요약을 카드에 |
| UI가 화면 ~60% 차지 | `#metrics` 숨김 + `updateMetrics()` 생략, 패널 header/body 분리 + 접기 토글 |
| "프러스텀"이 무슨 말인지 안 통함 | `카메라 경로`로 개명, 켜면 개수 표시 |

## 2. 성공한 것

### 2-1. 다중 시점 검증이 실제로 작동한다

실기기 스캔 결과의 관측 횟수 분포 변화:

| 스캔 | 키프레임 | 관측 1회 | 2회 | 3+회 |
|---|---|---|---|---|
| 1차 (6.6초) | 15/15 | 76% | 16% | **8%** |
| 2차 (9.5초) | 15/15 | 60% | 22% | **18%** |
| 3차 (18.0초) | 28/40 | 52% | 21% | **27%** |

`3+회`가 0이 아니라는 것이 이번 라운드의 핵심 결과다. `DepthCloud`의 프레임 중복 결함이 실제로 제거됐다는 뜻이다.

### 2-2. 복원이 실제 방 구조를 담는다

내보낸 JSON을 재구성해 관측 3+회 복셀의 높이 분포를 계산한 결과:

- **y = -1.10m에 날카로운 피크** (5cm bin 하나에 219개, 인접 bin은 82개) → **바닥 평면**
- **y ≈ -0.40m에 두 번째 봉우리** (115~122개) → 바닥 기준 **0.70m = 책상 높이**
- 카메라 평균 높이 y = +0.32 → 폰을 바닥 위 1.42m로 든 것과 일치

명세 Phase 2 진단표의 **"복셀이 방 형태를 대략 따라감 → 정상"** 행이다.

### 2-3. 필터가 전부 건강한 범위

3차 스캔(28 키프레임 × 14,400px = 403,200 샘플) 기준:

| 항목 | 값 | 예상 정상 범위 |
|---|---|---|
| 0값 버림 | 0% | 30–60% |
| 범위 버림 | 0% | 5–25% |
| 경사 버림 | 4.0% | 5–20% |
| 수용 | 96% | — |
| 재구성 시간 | 249ms (폰) | <400ms |

### 2-4. 목표 달성 가능성을 수치로 확인

클러스터링 없이 **바닥면 + 복셀 점유 + DDA 광선**만으로 (실측 데이터, 오프라인 계산):

- 바닥 위 후보 **181개**, 광선 **3,620개**를 **1ms 미만**에 계산 (폰 환산 ~6ms)
- 명세가 정한 적정 은신 구간(가림 0.4~0.8)에 **43개** 후보
- 바닥 통행 가능 칸 **640개**, 최장 경로 **4.8m**, 점유 충돌 **0회**
- 경로를 따라 가림 비율이 **100% → 0% → 10% → 0%** 로 변함 — "숨었다 나타났다"가 수치로 잡힘

occluder 삼각형 수도 문제없다: 임계 3에서 1,988복셀 × 12 = **23,856 삼각형**으로 하츄핑 모델(186,117)의 1/8이다. greedy meshing이 필요 없다.

## 3. 실패한 것과 한계

### 3-1. ⚠ 클러스터링으로 물체가 분리되지 않는다 (명세 Phase 4의 실패)

명세 4-1은 바닥 제거만으로 대부분 분리될 것으로 보고 벽 제거(4-2)를 "선택, 우선순위 낮음"으로 뒀다. **실측 결과 그렇지 않다.**

바닥 제거 방식을 세 가지로 바꿔가며 3D flood fill을 돌린 결과:

| 방식 | 잔존 셀 | 클러스터 수 | 최대 클러스터 비중 |
|---|---|---|---|
| 대칭 밴드 ±0.10m, 6-연결 | 1,484 | 44 | **85%** |
| 대칭 밴드 ±0.10m, 26-연결 | 1,484 | 11 | **93%** |
| 바닥면 이하 절단 +0.05m | 1,538 | 45 | **84%** |
| 바닥면 이하 절단 +0.25m | 1,380 | 44 | **89%** |
| (임계 2로 낮춤) 바닥면 이하 절단 | 3,598 | 94 | **96%** |

**밴드 폭과 무관하게 84~96%가 한 덩어리로 남는다.** 원인은 책상·의자·벽·모니터가 바닥을 거치지 않고 **서로 직접 붙어 있기** 때문이다. 바닥을 지워도 그 연결은 끊기지 않는다.

벽 제거를 축 정렬 히스토그램으로 시도하면 큰 덩어리는 깨지지만(85% → 26%) **1,484개 중 146개만 남아 방의 90%가 삭제된다.** 밀집한 X/Z bin이 벽뿐 아니라 책상·의자이기도 하기 때문이다. 밴드를 0.20m로 넓히면 15개만 남는다.

**결론: 이 방(책상이 벽에 붙은 코너)에서는 단순 기하 방법으로 물체 단위 분리가 안 된다.** 명세 Phase 7의 세그멘테이션이 필요한 지점이 바로 여기다.

### 3-2. 그러나 목표에는 클러스터링이 필요 없다

명세 6-1이 클러스터 bounding box로 후보를 만들라고 한 것은 편의였다. 실제로 필요한 것은:

- **Phase 5 occluder**: 점유 정보만 필요. 클러스터 불필요
- **Phase 6 은신처 판정**: 명세 6-2 자신이 "실제 렌더링 결과로 판정"(레이캐스트 가림 비율)이라고 못박고 있다. 클러스터 불필요
- **경로 계획**: 점유 격자 위 BFS로 충분. bounding box 불필요

§2-4에서 이미 수치로 확인했다. 따라서 **클러스터링은 진단·발표용으로만 남기기로 했다.** "해봤는데 이 방에서는 안 되더라"를 보여주는 것 자체가 발표 자료가 된다.

### 3-3. AR 오버레이가 아직 읽히지 않는다

영상에서 wireframe이 화면 전체를 덮는 죽처럼 나온다. 원인 두 가지:

1. 패널의 `minObservations`(=1)를 그대로 물려받아 노이즈 절반이 포함됨
2. `depthWrite: false` 때문에 **복셀끼리 서로 가리지 않아** 3D 부피 전체가 납작하게 겹쳐 보임

**반경 컬링은 이 방에서 무효다.** 실측: 반경 2m면 이미 전체(10,985/10,985)가 들어온다. 밀도를 줄이는 유일한 레버는 관측 임계값이다 (임계 3 → 1,988개, 5.5배 감소).

### 3-4. 키프레임 상한이 스캔을 조기 종료시켰다 (수정됨)

1·2차 스캔이 20초 중 **6.6초·9.5초**에 15장 상한으로 끝났다. 상한을 40장으로 올리고, ARCore depth 준비 전에 잡히는 빈 키프레임(14,400개 전부 0값)을 폐기하도록 고쳐 3차에서 18.0초/28장이 됐다.

### 3-5. 그 밖의 한계

- **세션 간 위치 복원 불가.** XRAnchor는 같은 세션 동안의 고정이 목적이다. JSON을 불러오면 좌표가 다른 XR local 원점 소속이라 AR 오버레이를 강제로 끈다.
- **명세의 오류 하나.** "부피 20cm³ 미만 클러스터 삭제"는 5cm 복셀 하나가 125cm³라 아무것도 지우지 않는다. 셀 개수로 표현해야 한다.
- **바닥 아래 복셀 7.5%는 노이즈가 아니다.** 전부 바닥 바로 아래 한 칸(-1.15m)이며 바닥면 자체의 두께다. 깊은 바닥밑 노이즈는 실측상 존재하지 않았다.

## 3-6. 2차 실기기 검증 (3.7분 녹화, 44프레임 분석)

거실 전체를 도는 더 긴 스캔으로 다시 확인했다.

### 잘 된 것

| 항목 | 1차 | 2차 |
|---|---|---|
| 키프레임 | 28/40 @ 18.0s | 40/40 @ 16.2s |
| 복셀 (0.05m) | 19,330 | **61,990** |
| 복셀 (0.04m) | — | 90,535 |
| 0값 버림 | 0 | 0 |
| 범위 버림 | 0% | 1.0% |
| 경사 버림 | 4.0% | 8.7% |
| 재구성 | 249ms | 487ms (0.05m) / 717ms (0.04m) |

- **복원이 실물을 정확히 잡는다.** 임계값 4에서 검은 쓰레기통 자리에 박스 기둥이 서고 바닥에 평면이 깔린다. 운영자 뷰에서 바닥 평면과 그 위 구조물이 명확히 구분된다.
- **재스캔 없는 재필터가 실기기에서 증명됐다.** 같은 스캔에서 임계값 1→2→4, 복셀 0.05→0.04를 전환하며 표시 개수가 61,990 → 21,265 → 6,145로 즉각 반응했다.
- **검은 물체 아티팩트를 필터가 잡아낸다.** 검은 원통에서 카메라 쪽으로 길게 번진 덩어리가 임계값 1에서는 보이지만 4에서는 사라지고 물체 자리에만 기둥이 남는다. 검은 표면은 depth 센싱이 취약해 생기는 전형적 아티팩트인데, 다중 시점 필터가 실제로 걸러낸다는 증거다.
- occluder 메시가 48,016 / 36,060 삼각형으로 생성됐고 켜면 wireframe이 잘려나간다.

### 문제

1. **가림 테스트가 사실상 수행되지 않았다.** 게임을 시작한 뒤 끝까지 가림 메시가 꺼진 채였다. 하츄핑이 소파 앞에 그대로 떠 있는 화면은 "가림이 안 된다"가 아니라 "가림을 안 켰다"였다. 진단 모드에서 게임을 켜는 이유가 가림 확인 하나뿐인데 수동 토글로 둔 설계 실수. 게임 시작 시 자동으로 켜지게 고쳤다.
2. **재구성이 느리다.** 0.04m에서 717ms로 건강 기준(400ms)을 넘는다. 슬라이더 드래그가 버벅인다.
3. **키프레임 40장을 16.2초에 소진한다.** 20초 중 3.8초가 버려진다. 상한을 올리면 재구성이 더 느려지는 트레이드오프.
4. **occluder를 켜면 AR 오버레이가 거의 사라진다.** 둘이 같은 표면을 그리므로 당연한 결과지만, "정렬이 맞나"를 확인하는 용도로는 무용해진다. 검증 방법을 다시 설계해야 한다.
5. **관측 3+ 비율이 27%에서 17%로 낮아졌다.** 방이 넓어져 더 많은 표면을 한 번씩만 본 결과다. 커버리지와 신뢰도의 트레이드오프이며 임계값 슬라이더로 대응 가능하다.

## 5. 다음에 할 것

### 우선순위 (2차 검증 후 갱신)

1. **재구성 속도** — 717ms는 슬라이더를 못 쓰게 만든다. 재구성을 증분화하거나 복셀 크기 하한을 올린다
2. **가림 검증 방법 재설계** — occluder와 오버레이가 서로를 지우므로, occluder를 반투명 색으로 볼 수 있는 진단 전용 표시가 필요하다
3. **색상 언어 충돌** — 복셀의 빨강(관측 1회 = 신뢰도 낮음)과 통행 타일의 빨강(설 곳 없음)이 정반대 의미다. 복셀 쪽을 단색 그라데이션으로 바꾸는 편이 낫다
4. 아래 클러스터링

### Stage B (진행 중) — 진단용 클러스터링
- `voxel-cluster.js`: 3D flood fill, **6-연결 기본**(26-연결은 7cm 떨어진 표면 껍질을 대각선으로 이어붙임), 반복문 필수(재귀는 수천 셀 연쇄에서 스택 오버플로 확정), 정수 키 맵
- 작은 클러스터는 버리지 않고 `clusterId = -1` + 어두운 회색
- `VoxelGrid.clearClusterIds()` — 임계값을 바꾸면 제외된 셀에 stale id가 남는 함정
- `largestShare > 0.8`이면 HUD에 `⚠ 단일 덩어리` — **이 방에서는 항상 뜰 것이고, 그게 §3-1의 한계를 보여주는 화면이다**
- 바닥·클러스터는 **선택 파이프라인**에 넣는다(재구성이 아니라). 임계값 드래그마다 249ms 재구성이 돌면 안 되므로

### Stage C — Phase 5 occluder 메시
- `voxel-occluder-mesh.js`(순수) + `voxel-occluder.js`(어댑터)
- **병합 BufferGeometry**, InstancedMesh 아님 — 인스턴싱은 면 컬링과 greedy meshing을 원천 차단한다
- `Uint32Array` 인덱스 (정점 ~92,000개로 Uint16 한계 초과)
- `cellCenterPosition` 사용 — 평균 위치 박스는 타일링이 안 돼 면 컬링 시 틈이 생긴다. **부작용**: 디버그 wireframe(평균)과 occluder(격자)가 최대 2.5cm 어긋나 보임
- `colorWrite:false, depthWrite:true, polygonOffset:true, renderOrder:-3`
- 박스를 줄이지 않는다. 깊이 여유는 전부 `polygonOffset`으로 — 고정 월드 오프셋과 달리 모든 각도에서 옳다
- AR 오버레이 가독성도 여기서 해결: **깊이 선패스**(보이지 않는 solid로 깊이를 채우고 wireframe을 `depthTest`로) + 오버레이 전용 임계값

### Stage D — Phase 6 은신처와 이동
- `voxel-raycast.js`: 복셀 격자 DDA. 삼각형 메시 레이캐스트가 아니라 BVH가 필요 없고 순수 로직이라 테스트가 쉽다
- `hiding-spots.js`: 바닥 격자 생성 + 가림 비율 0.4~0.8 채택 + BFS 경로
- 이동 중 렌더링 가림은 **추가 작업 없음** — occluder가 깊이를 한 번 쓰면 GPU가 매 프레임 픽셀 단위로 처리한다. 캐릭터가 어디로 가든 프레임당 CPU 비용 0

### 모드 설계
`APP_MODES`에 값을 추가하지 않고 직교 파라미터 `?occluder=voxel`로 간다. `resolveAppMode`는 "어떤 depth 파이프라인인가"의 단일 승자 체인이고, "가림을 어디서 얻나"는 다른 축이다.

| URL | 용도 |
|---|---|
| `?voxel=debug` | 디버그 UI 전체 |
| `?occluder=voxel` | **데모 구성** — 일반 게임 + 정적 복셀 occluder |
| `?occlusion=cpu&occluder=voxel` | 명세의 병행 구조 |

`NinjaGame.startSession()`이 `startMapping(MAP_SECONDS=20)`으로 열고 `VOXEL_SCAN_SECONDS`도 20이라, 같은 20초 걷기에 동시에 돈다. **새 스캔 UX가 필요 없다.**

## 6. 남은 위험

1. **occluder z-fighting** — 하츄핑 발이 잘릴 수 있다. `polygonOffset`으로 완화하되, 20초 스캔의 pose 드리프트가 그 도달 범위를 넘으면 offset을 더 키우지 말고(벽 뚫림이 생긴다) 수평면에만 -Y 월드 오프셋을 준다.
2. **바닥 검출이 책상을 고를 위험** — 하위 백분위 창으로 차단했으나, 바닥을 한 번도 못 본 스캔은 어떤 알고리즘도 구하지 못한다. HUD 신뢰도 수치가 재스캔하라고 알려주는 역할.
3. **은신처가 너무 잘 숨음** — 실측 분포에서 완전은폐(0.8~1.0)가 73개로 적정(43개)보다 많다. 방에 따라 적정 구간이 빌 수 있는데, 그때는 구간을 넓히지 말고 후보 격자를 조밀하게(10cm→5cm) 한다.
